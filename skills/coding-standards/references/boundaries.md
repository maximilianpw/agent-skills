# Boundaries and ownership

## Parse at trust boundaries

Treat network payloads, environment variables, files, messages, user input, and untyped SDK results as untrusted. Parse them with the repository's existing schema or validation library and expose the parsed type inward.

A TypeScript annotation does not validate runtime data. Keep parsing and translation near the boundary that knows the external representation.

Database rows generated by a typed ORM do not need an automatic second parse. Re-parse persisted data when it may predate current invariants, bypass the application, contain schemaless fields, or otherwise drift independently.

## Own technology locally

- HTTP request objects belong to the transport adapter.
- ORM models and rows belong to the persistence adapter.
- Vendor SDK objects belong to the integration adapter.
- Domain and application modules communicate in application-owned types.

Define dependencies from the consumer's needs rather than mirroring a provider API. Prefer a narrow capability over a broad dependency bag or service locator.

## Scoped modules and shared behavior

Place a reusable operation at the narrowest common owner of callers that need **the same semantics**. A module may import rules owned by its folder and broader modules above it; TypeScript imports make that stack explicit. Promote behavior upward only when a second scope genuinely shares its contract, not merely because similar code appears elsewhere.

Name modules after the behavior they own (`host.ts`, `cookie-domain.ts`), rather than adding `utils.ts` at each directory level. Keep provider-specific policy with its provider and cross-application parsing in a shared owner. For example, Better Auth cookie policy may use a shared host parser, but cookie shareability does not become a general host-trust rule.

Inspect **services as well as helpers** for repeated small behavior. Trace each occurrence's inputs, failure behavior, effect order, and trust assumptions before consolidating it. Move an equivalent pure rule into its narrowest owning module; when the repeated behavior coordinates dependencies or effects, put it behind the cohesive service that owns that operation. Keep distinct policies visible at their call sites even when they share a mechanism.

Apply the deletion test to an extraction: if removing the new module would spread meaningful behavior back across callers, it earns its interface; if it only forwards calls, leave the code with its owner. A folder move clarifies ownership but does not by itself justify another service or export. Verify the affected behavior through the owning service interfaces and callers after moving code.

## Services and composition

- Put pure rules and invariants in domain modules.
- Put sequencing, fallback, retry, and transaction policy in the use-case owner.
- Put serialization, protocol mechanics, and provider-specific errors in adapters.
- Construct dependencies at an entrypoint or another explicit composition root.
- Inject time, randomness, and external capabilities when deterministic tests or alternate implementations matter.
- Keep modules import-inert: importing a module should not read configuration, connect to infrastructure, or start work.

An abstraction should hide real complexity or stabilize a real boundary. Prefer direct code when an interface would have one caller, one implementation, and no meaningful policy to hide.

## Configuration and secrets

- Read and parse configuration once at startup or at the framework's established configuration boundary.
- Pass typed configuration inward; do not scatter environment-variable reads through business code.
- Validate cross-field configuration rules before serving work.
- Keep secret values out of logs, traces, errors, snapshots, and serialized configuration.
- Unwrap a secret only at the final call that needs it.

## Persistence and workflows

- Translate between persistence and domain representations in the persistence owner.
- Keep transaction scope in the application operation that owns atomicity.
- Do not hold transactions open across unrelated network calls without an explicit design reason.
- Make redelivered messages and retried workflows idempotent. Store the idempotency decision with the side effect when races matter.
- Record enough durable state to resume multi-step work safely; in-memory progress is not a workflow guarantee.

## Observability

- Establish correlation at the entry boundary and propagate it through owned dependencies.
- Log stable event names and safe structured fields.
- Record failures once at the boundary that has the necessary context; avoid duplicate logging at every layer.
- Metrics and traces should describe domain or application operations, not expose secret payloads.

## Completion check

- Every external representation stops at a named owner.
- Repeated helper and service behavior has one narrow owner when semantics match; distinct policies remain visible and independently testable.
- Configuration, resources, side effects, transactions, and detached work each have an explicit lifetime owner.
- Domain code receives application types and capabilities rather than framework or provider objects.
