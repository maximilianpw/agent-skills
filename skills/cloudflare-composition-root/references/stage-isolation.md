# Stage-isolated infrastructure

Use this when an Alchemy Stack, stage, shared-infrastructure package, or cross-Stack resource reference changes.

## One topology per stage

Every environment (production, preview, test, local) gets isolated infrastructure with the same capability topology. Preview and test stages provision their own live resources. Local stages use faithful local providers where Alchemy supplies them; when one missing local provider forces a connected subsystem to stay live, provision that whole subsystem as stage-owned infrastructure and document the exception. Local, preview, and test data flow only through their own stage's resources.

## Ownership versus location

A resource definition's package location does not decide which Stack owns its lifecycle. Keep cohesive shared definitions in the shared-infrastructure package, and assign each resource to the Stack whose lifecycle should create, replace, and destroy it. An application Stack references a shared resource; it does not redefine it to make local development work.

## Ordering and provider mode

When an application Stack depends on a shared Stack:

- create the shared Stack first and destroy it last;
- run both Stacks under the same Alchemy stage and provider mode;
- propagate dynamically generated test stages through the test runner or harness, because a static task prerequisite cannot know a stage generated by a later command.

Alchemy chooses local or live providers when the owning resource is provisioned. A Queue owned by a shared Stack gets a local identity and broker only when that shared Stack itself runs locally (`alchemy dev` or a dev-mode test). A local application referencing the production shared Stack receives the live Queue; task ordering does not turn it local. Keep the same native binding in local and deployed Workers and fix the owning Stack's stage and provider orchestration, rather than swapping the binding for an HTTP capability.

## Permanent resources

Place a resource in an explicitly permanent stage only when sharing it across stages is a deliberate exception, such as a shared observability dataset or a reusable account policy. A stage-specific shared Stack may reference those permanent outputs while owning everything that needs isolation. Fixed-name account resources are provisioned once, not per preview. Production may keep established physical names; other stages use Alchemy-generated or stage-qualified names, and their retention policies let ephemeral stages be destroyed.

## Completion check

Every changed cross-Stack dependency records whether the resource is permanent or stage-isolated, which Stack owns it, how its local provider is selected, and how creation and destruction are ordered; every non-production stage uses only its own or explicitly permanent resources; and non-production names and retention policies allow the stage to be destroyed.
